## 第 2 页 · 问题（0:00–0:35）

**游客在西安找美食，卡在哪？**

- 不知道一道菜是什么、怎么吃
- 攻略、短视频、点评内容碎片化
- 不知道该去餐馆、街边摊、美食街还是巷子小店
- 价格、评分、营业状态可能已经变化
- 看到推荐后仍然无法决定去哪、何时去、怎样串联

> 一句话：信息很多，但能落地执行的很少。

---

## 第 3 页 · 方案（0:35–0:50）

**先看懂一味，再走进一街。**

以西安美食图鉴为入口，连接真实地点、门店菜单、价格、营业状态和消费方式，帮助游客发现、理解、比较并规划一次可执行的西安美食探索。

核心闭环：
浏览图鉴 → 了解菜品 → 找到真实地点 → 选择吃法 → 生成路线 → 核验来源 → 出发

## 第 6 页 · 产品展示 · 路线（1:30–2:05）

**去哪吃，怎么吃**

输入：钟楼附近、两小时、150 元、三种小吃、不想去连锁店

输出：
- 三个真实地点、访问顺序
- 每站推荐菜品与消费方式
- 预计预算与步行时长
- 营业与排队风险提示
- Plan B 备选方案

## 第 7 页 · 产品展示 · 来源核验（2:05–2:30）

**每一条信息都有来处**

- 菜品历史：百度百科词条，可点击跳转
- 店铺信息：游陕西小程序截图，含 2026 必吃榜标识
- 评分缺失：统一展示 90.0 并显式声明「展示规则补全」
- 营业状态：标注「以门店实时状态为准」，不声称实时

## 第 8 页 · 技术架构（2:30–3:10）

```
用户自然语言输入
→ 规则解析（agentApi，保留大模型接入边界）
→ 查询菜品图鉴（atlasApi）
→ 查询真实地点（atlasApi）
→ 组合路线（routeApi）
→ 确定性计算：预算、时长、风险
→ 输出方案 + 来源
→ 天地图标注同步更新
```

技术栈：
- 前端：React 18 + Vite
- 地图：天地图 Web API v4.0
- 数据：本地 seed + source registry（断网可演示）
- 视觉：changan-ink-ui 国风深色范式

## 第 9 页 · 创新点（3:10–3:40）

1. **图鉴与真实地点联动** — 从一道菜直接进入可验证店铺
2. **菜品—地点—消费方式—路线四层关系** — 不是看完百科就结束
3. **文化内容与消费决策结合** — 解释「这是什么」+「去哪吃、怎么吃」
4. **证据化数据** — 每条信息标注来源、采集时间、验证状态
5. **天地图真实标注** — 不是示意图，是可定位的真实地图
6. **AI + 确定性工具** — AI 负责理解，程序负责价格、距离、营业校验

## 演讲备注

### 第 2 页
不要念列表，讲一个场景：「一个游客到了西安，打开点评看到几千家店，刷短视频看到几十个推荐，但还是不知道今晚去哪吃。」

### 第 4 页
现场操作：打开 Demo，等轮播自动切换两张，然后点击一张卡片打开详情弹窗，指着来源链接说「这条历史可以跳到百科核验」。

### 第 5 页
现场操作：切到地图板块，点击一个标注，展示底部卡片，再点「查看味道」打开菜品弹窗。

### 第 6 页
现场操作：在输入框输入条件（或点预设），点生成，等地图标注切换，然后逐个点击站点卡片。

### 第 8 页
不用讲代码，讲分工：「AI 负责理解你说的话，程序负责算价格、算距离、校验营业状态，两者各司其职。」

### 第 11 页
强调诚实：「我们没有编造评分，没有的分数就标 90.0 并说明这是展示规则。评委可以打开来源抽屉逐条核验。」
